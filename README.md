# Планировщик ликвидности и денежных потоков

Автоматизированная система внутрибанковского операционного планирования и управления лимитами ликвидности.

## Описание проекта

Планировщик ликвидности и денежных потоков — это веб-дашборд для казначейства, риск-менеджмента и руководства банка. Система помогает контролировать текущую и прогнозную ликвидность, видеть кассовые разрывы, управлять заявками подразделений, отслеживать лимиты и фиксировать действия пользователей в журнале аудита.

## Актуальность

В банках планирование ликвидности часто выполняется вручную: через Excel, бумажные заявки и переписку между подразделениями. Такой процесс повышает риск ошибок, задержек согласования, кассовых разрывов и неэффективного использования свободных денежных средств.

Проект решает эту проблему за счет единого интерфейса, где денежные потоки, лимиты, заявки, роли и прогнозы сведены в одну операционную картину.

## Цель

Разработать прототип автоматизированной системы для:

- расчета текущей и прогнозной ликвидности;
- контроля лимитов по валютам;
- обработки заявок подразделений;
- согласования операций;
- выявления риска кассового разрыва;
- ведения журнала аудита;
- подготовки управленческой отчетности.

## Серверный контур

В проект добавлены серверные API-точки:

| Маршрут                         | Назначение                                                    |
| ------------------------------- | ------------------------------------------------------------- |
| `GET /api/health`               | Проверка состояния сервиса и логической базы `DB`             |
| `GET /api/liquidity/summary`    | Сводка ликвидности, предупреждения и источники данных         |
| `GET /api/requests`             | Реестр заявок и маршрутов согласования                        |
| `GET /api/limits`               | Чтение минимальных лимитов ликвидности из D1                  |
| `POST /api/requests`            | Создание заявки с записью в D1 и серверной проверкой роли     |
| `PATCH /api/requests`           | Согласование или отклонение заявки с серверной проверкой роли |
| `PATCH /api/limits`             | Изменение лимита с серверной проверкой роли риск-менеджера    |
| `GET /api/audit`                | Чтение серверного журнала аудита из D1                        |
| `GET /api/industrial-readiness` | Статус 10 доработок до промышленной версии                    |

## База данных

Добавлены файлы:

- `db/schema.ts` — SQL-схема банковских сущностей;
- `drizzle/0001_bank_core.sql` — миграция для D1/SQLite.

Схема включает таблицы пользователей, денежных потоков, лимитов, заявок, журнала аудита, источников интеграции и уведомлений.

Заявки, лимиты и аудит теперь проходят через серверный API: создание заявки, решение по заявке, изменение лимита и контрольные события записываются в D1, а сервер отдельно проверяет роль пользователя. Если сайт открыт в статической версии GitHub Pages, где серверные API недоступны, интерфейс автоматически остается в демонстрационном локальном режиме.

## Архитектура будущей версии

Промышленная версия системы должна включать:

- пользовательский интерфейс для сотрудников банка;
- серверный интерфейс программирования приложения для расчетов, заявок, лимитов и аудита;
- базу данных для хранения операций и истории действий;
- интеграционный слой с АБС, кредитным, депозитным и валютным модулями;
- сервис уведомлений;
- модуль отчетности;
- модуль безопасности и ролевого доступа.

## Что реализовано в текущем прототипе

Текущая версия является интерактивным прототипом пользовательского интерфейса с добавленным серверным контуром. Демо-сценарий на экране сохраняется в локальном хранилище браузера, а для промышленной версии подготовлены API-маршруты, логическая база `DB`, SQL-схема и миграция.

Дополнительно добавлен презентационный слой: паспорт проекта, готовность модулей, ожидаемый эффект для банка, сценарий демонстрации и ответы на возможные вопросы комиссии.

Для защиты добавлен отдельный режим презентации. Он возвращает прототип к начальному состоянию, открывает раздел «Защита» и позволяет показать проект в правильной последовательности.

## Ограничения текущей версии

- Данные являются демонстрационными.
- Заявки, лимиты и журнал аудита в пользовательском сценарии пока сохраняются в локальном хранилище браузера.
- Полная авторизация требует SSO, LDAP, Active Directory или внутренний IAM банка.
- Реальные интеграции с АБС, депозитами, кредитами и валютными операциями требуют тестовых доступов банка.
- PDF-отчет формируется как печатная форма для демонстрации; промышленная версия должна использовать утвержденные формы банка.

## Что нужно доработать для промышленной версии

1. База данных — подготовлен D1 binding `DB`, схема, миграция, сохранение заявок, решений и лимитов.
2. Серверный API — добавлены маршруты для состояния, сводки, заявок, лимитов и готовности.
3. Полноценная авторизация — требуется политика идентификации банка.
4. Серверная ролевая модель — добавлена проверка роли при создании/согласовании заявки и изменении лимита, нужна привязка к SSO.
5. Реальные банковские источники — требуются тестовые API/выгрузки банка.
6. Маршруты согласования — спроектированы по сумме, валюте, типу операции и риску.
7. Неизменяемый журнал аудита — подготовлена схема hash-chain.
8. Уведомления и эскалации — подготовлена модель событий, нужны SMTP/SMS/внутренний шлюз.
9. Отчеты в электронных таблицах и PDF — усилены выгрузки CSV, XLS и печатная PDF-форма.
10. Тестирование безопасности и нагрузки — подготовлен чек-лист испытаний.

## Сценарий презентации

1. Нажать «Начать защиту».
2. Объяснить проблему ручного планирования ликвидности.
3. Показать главный дашборд и прогноз.
4. Переключить сценарии прогноза.
5. Создать новую заявку.
6. Показать изменение прогноза после заявки.
7. Согласовать или отклонить заявку.
8. Показать журнал аудита.
9. Переключить роли пользователей.
10. Показать настройку лимитов от роли риск-менеджера.
11. Выгрузить отчет.
12. Открыть архитектуру, ограничения и вкладку с доработками до промышленной версии.
